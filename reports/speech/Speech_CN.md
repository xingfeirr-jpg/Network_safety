# Project 17 演讲稿（中文版）

> 三款静态漏洞检测工具在十个开源 C 库上的比较 · 结合 Web 界面演示
> 建议时长：约 12–15 分钟（可按 ⏱ 标注删减）
> 演示地址：本地 `http://localhost:8000`（含实时运行）或 GitHub Pages 静态版
> 【操作】= 在界面上的动作；正文 = 要讲的话

## 0. 开场（约 30 秒）

大家好，我们是 Project 17 小组。今天汇报的题目是：**三款静态漏洞检测工具在十个开源 C 库上的比较**。

先问一个问题：静态分析工具报出来一条“可能缓冲区溢出”，这条告警能不能直接信？我们的做法很直接——把三款工具在十个库上报出的 **725 条告警，一条一条对回源码核查**，再用核查结果反过来评价工具本身。

整个汇报我会结合我们做的 Web 界面来讲，顺序就是界面上的标签页。

---

## 1. 项目总览（约 1 分钟）

【操作】打开首页“项目总览”。

这一页是整个项目的摘要。

- **3 款工具**：Flawfinder、Cppcheck、CodeChecker 搭配 Clang 静态分析器（下面简称 clangsa）。
- **10 个开源 C 库**，涵盖压缩、JSON、YAML、XML、图像和 Unicode 六个领域。
- **30 次扫描**，一共得到 **725 条告警**。

右边这张图是三款工具的核查结论。先给大家一个最直观的结果：725 条里，**648 条是误报，62 条有依据，15 条无法判断**。也就是说，将近九成的告警，回到源码一看，风险并不成立。

下面这些卡片是各个模块的入口，我们按顺序往下看。

---

## 2. 库数据（约 1 分钟）

【操作】点击“库数据”标签。

这是十个被测库。每个库都**锁定到具体的 commit**，并记录了源码包的 SHA-256 哈希，保证我们分析的是同一份代码。

两个数字需要解释一下：

- **编译动作**：Cppcheck 和 clangsa 以“一次编译”为分析单位。比如 libjpeg-turbo 要按 8 位、12 位、16 位三种配置各编译一遍，所以 58 个源文件对应 101 个编译动作。
- **Flawfinder 扫描文件**：Flawfinder 不编译，直接读文本，所以 `.c` 和 `.h` 都算。

【操作】切换上方的库，展示扇形图。

扇形图显示每个库的告警由哪个工具报出、结论是什么。可以看到，同一个库里，三款工具报出的告警数量差别非常大。

---

## 3. 工具介绍（约 1.5 分钟）

【操作】点击“工具介绍”。

三款工具都是静态分析，不运行程序，只读代码。区别在于“读得有多深”。打个比方：

- **Flawfinder 是“查关键词”**：文章里出现“炸弹”两个字就报警。它逐行扫描，看到 `memcpy`、`strcpy`、`strlen` 这类危险函数名就报。不需要编译，速度极快，但不理解代码。
- **Cppcheck 是“读懂句子”**：它跟踪变量可能的取值，判断用法有没有问题。需要编译数据库。
- **clangsa 是“推演整个故事”**：用真实的 Clang 编译器前端，把输入当作未知数，沿着每条分支模拟执行，看错误能不能被走到。最深，也最慢。

【操作】向下滚动到“匹配规则”。

这里列出了每款工具具体的报警维度和计数口径。比如 Cppcheck 我们只统计非 information 级别的告警，多个位置只算一次。**计数口径统一，三款工具的数字才可以放在一起比较。**

## 4. 实时运行（约 2 分钟）⏱ 时间紧可只讲流程、不现场跑

【操作】点击“实时运行”。

这一页展示我们的实验流程是**可以现场复现**的。上面是 S1 到 S6 六个步骤：

- S1 下载：按固定 commit 下载源码，核对哈希
- S2 源码：解包，并记录每个文件的哈希
- S3 构建：用原实验的 CMake 选项构建，导出编译数据库
- S4 命令：按冻结配置生成和原实验逐字节相同的工具命令
- S5 运行：运行工具，用 GNU time 记录耗时和内存
- S6 比对：把这次的结果和原实验逐条比对

【操作】选择 zlib + Flawfinder，点击“开始运行”。

现在后端会在 Docker 容器里真正执行这个工具。容器里的工具版本是锁死的：Flawfinder 2.0.20、Cppcheck 2.13.0、CodeChecker 6.29.1、Clang 18.1.3。

【操作】等待完成，指向结果。

运行完成。这次得到 **49 条告警，和原实验的 49 条完全一致**。也就是说，任何人拿着我们的仓库，都可以得到同样的结果。

## 5. 数据看板（约 1.5 分钟）

【操作】点击“数据看板”。

这是 725 条告警的全景。

- **判定分布**：Flawfinder 报了 536 条，占总数的七成多，但其中只有 **5 条**有依据。Cppcheck 报了 116 条，有依据 **39 条**。clangsa 报了 73 条，有依据 **18 条**。
- **运行耗时**：差距同样很大。Flawfinder 单次运行中位数只要 **0.13 秒**；Cppcheck 是 **5.44 秒**；clangsa 是 **28.33 秒**，比 Flawfinder 慢两百多倍。
- **高频规则**：Flawfinder 的前三名是 `memcpy`、`strlen`、`char`，全是“名字匹配”型的规则。

【操作】在告警列表中筛选，点开任意一条。

每条告警都可以点开看详情：位置、规则、源码，以及**核查理由**——为什么判成误报，或者为什么有依据。这就是我们 725 条逐条核查的证据。

## 6. 案例分析（约 3.5 分钟）

【操作】点击“案例分析”。

我们把 725 条告警按“判定逻辑”归成了 19 个案例族。下面挑三个最有代表性的，分别对应：**最浅的工具为什么错、最深的工具为什么也会错，以及真正的问题长什么样**。

### 案例一：变量名叫 `strlen`，Flawfinder 报了 18 次（误报 · 名字匹配，不是调用）

【操作】打开“名字匹配，不是调用”这一族，展示 utf8proc 的例子。

```c
utf8proc_iterate(const utf8proc_uint8_t *str, utf8proc_ssize_t strlen, utf8proc_int32_t *dst) {
  ...
  if (!strlen) return 0;                     // 检查长度是否为 0
  end = str + ((strlen < 0) ? 4 : strlen);   // 用长度算读取边界
```

utf8proc 里有一个**整数参数**，名字恰好叫 `strlen`。它是一个长度值，代码先检查它是不是 0，再用它算读取边界，**根本没有调用 strlen 函数**。

但 Flawfinder 只看名字，看到 `strlen` 就报“可能越界读”。在 utf8proc 这一个库里，Flawfinder 报了 **18 条告警，全部是这个 `strlen`，全部是误报**。而 Cppcheck 和 clangsa 理解这是一个变量，一条都没报。

这一类“名字对上了，其实不是调用”的误报，在 9 个库里一共有 **70 条**。这说明了 Flawfinder 的根本局限：**它不懂语法，分不清函数名和变量名。**

### 案例二：“出错就退出”，深度工具也会误判（误报 · 错误处理不返回）

【操作】打开“错误处理不返回”这一族，展示 libjpeg-turbo `jdapistd.c:211`。

```c
  if (!xoffset || !width)                    // 207 行
    ERREXIT(cinfo, JERR_BAD_CROP_SPEC);      // 208 行

  /* xoffset and width must fall within the output image dimensions. */
  if (*width == 0 ||                         // 211 行
```

clangsa 报告：第 211 行可能对空指针 `width` 解引用。它的推理是：如果 `width` 为空，执行会走到 211 行。

但是在 207–208 行，`width` 为空时会先调用 `ERREXIT`。这个宏会调用错误处理回调 `error_exit`，而 libjpeg 的文档明确规定这个回调**不允许返回**——默认实现直接 `exit`，自定义实现也必须 `longjmp` 跳走。所以空指针**根本走不到 211 行**。

这一行，clangsa 在 8 位和 12 位两种构建配置下各报了一次，Cppcheck 也报了一次。这一类误报总共 **88 条**，三款工具都有，几乎全部集中在 libjpeg-turbo。

这个案例说明：**即使是最深的路径分析，也看不到写在文档里的约定**。工具不知道“这个函数永不返回”，就会推演出一条实际不存在的路径。

### 案例三：zlib 的 `memcpy` 真的可能越界（有依据 · 条件性溢出）

【操作】打开“条件性溢出”这一族，展示 zlib `gzwrite.c:217`。

```c
            copy = state->size - have;           // 214 行：剩余空间
            if (copy > len)
                copy = (unsigned)len;
            memcpy(state->in + have, buf, copy); // 217 行
```

前面两个是误报，最后看一个**有依据**的。

这条告警的容量检查依赖一个前提：已写入的量 `have` 不超过缓冲大小 `size`。但在**非阻塞写入**模式下，`gzprintf` 可以合法地让 `have` 处在 `size` 和 `2×size` 之间。这之后再调用一次小的 `gzwrite`，`size - have` 这个无符号减法就会**下溢**，变成一个很大的数，于是 `copy` 不再被截断，`memcpy` 写入的数据会**超过已分配的堆缓冲区**。

有意思的是：这条有依据的告警，**只有 Flawfinder 报了**，Cppcheck 和 clangsa 都没有报。误报最多的工具，偏偏抓到了另外两款漏掉的问题。

需要强调边界：这是**源码层面**的推导，我们没有做动态复现，也没有评估它能不能被远程利用。

**三个案例的小结**：浅层工具会因为不懂语法而误报；深层工具会因为不懂项目约定而误报；而真正的问题，可能恰恰藏在“噪音最大”的工具里。

## 7. 结论（约 3 分钟）—— 重点

【操作】点击“总结评估”。

最后是结论。这一页每个数字都来自逐条核查过的告警，而不是工具自己报出的数量。我们从**准确性、成本、覆盖面**三个维度来看。

### 第一，准确率差距非常大

| | Flawfinder | Cppcheck | clangsa |
|---|---|---|---|
| 告警数 | 536 | 116 | 73 |
| 有依据 | 5 | 39 | 18 |
| 准确率 | **0.9%** | **33.6%** | **24.7%** |
| 每找到 1 条有依据，需要看 | **107 条** | **3 条** | **4 条** |

Flawfinder 每找到一条有依据的告警，平均要人工看 **107 条**；Cppcheck 只要 **3 条**，clangsa 约 **4 条**。对审计人员来说，这是一百多倍的人工成本差距。

### 第二，运行成本正好反过来

Flawfinder 中位耗时 **0.13 秒**，峰值内存约 25 MB；Cppcheck **5.44 秒**；clangsa **28.33 秒**，峰值内存两百多 MB。而且后两者都**必须先把项目构建起来**，拿到编译数据库才能分析，Flawfinder 什么都不需要。

所以**机器成本和人工成本是此消彼长的**：Flawfinder 机器上便宜，人工上昂贵；clangsa 正好相反。

### 第三，覆盖面：三款工具找到的问题几乎不重合

- Flawfinder 在全部 **10 个库**都有告警，Cppcheck 在 **6 个**，clangsa 只在 **4 个**。
- 三款工具各自在 4 个库里找到了有依据的问题，但**是不同的 4 个库**：
  - Flawfinder：zlib、libpng、yyjson、libjpeg-turbo
  - Cppcheck：LZ4、cJSON、yyjson、libjpeg-turbo
  - clangsa：zlib、LZ4、libpng、libjpeg-turbo
- 发现的问题类型也不同：Cppcheck 主要是可移植性和冗余检查（比如负数右移、冗余的空指针判断）；clangsa 主要是死存储、空指针这类路径相关问题；Flawfinder 偶尔能抓到真实的缓冲区问题，比如案例三。

**没有一款工具能替代另外两款。**

### 第四，什么时候用哪一款

- **成本敏感、只想快速过一遍**：用 Flawfinder 列出所有危险 API 的位置，但要做好大量人工筛选的准备。
- **CI 流水线里的常规质量检查**：Cppcheck 的性价比最高，准确率最高，速度可以接受。
- **关键模块的深度审计**：clangsa 能做路径敏感的分析，适合愿意为少量高价值告警花时间的场景，建议只对核心代码跑。
- **最好的做法是组合使用**：先用一款工具广覆盖、缩小范围，再用另一款对热点深挖，因为三款工具的告警集合基本不重合。

### 第五，结论的边界

我们也要说清楚这些结论**不能**推广到哪里：

1. 结论只针对**当前固定构建配置**下的源码行为，不代表其他版本或实际部署环境。
2. “有依据”表示问题在**源码层面成立**，**没有**做动态利用验证。
3. 只覆盖了 **10 个 C 库**，没有 C++ 或其他语言。
4. 工具版本固定，新版本的表现可能不同。

## 8. 可靠性（约 1 分钟）⏱ 时间紧可压缩

【操作】点击“可靠性”。

最后简单说一下，我们怎么保证这些结论站得住。用了两套机制。

**机制一：独立复现。** 一名成员完成原实验，只交出源码哈希和工具版本，不交出任何中间产物；另一名成员在干净的 Docker 环境里从头重跑。结果：**30 组运行，告警全部一致，命令全部逐字一致**；有哈希记录的 9 个库，源码包哈希也全部一致（cJSON 原实验没有记录哈希）。

**机制二：AI 分析 + 分层抽样人工复核。** 725 条告警先由 AI 对照源码逐条给出判定和理由。复核方案是：有依据和无法判断这两组共 77 条**全部逐条复核**；648 条误报按“工具 × 排除理由”分层抽样，总共抽取 200 条，随机种子固定，可重复。

这里要如实说明：**人工复核表已经生成，但还没有填写完成**，所以 AI 判定的一致率目前还没有数据。另外复现由项目内成员完成，不是外部第三方。这些是我们下一步要补上的地方。

## 9. 结尾（约 20 秒）

总结一句话：**告警多不等于有用，准确率高也不等于找得全。** 三款工具各有盲区，按场景组合使用，再配合人工核查，才是可靠的做法。

## 附：可能被问到的问题

- **为什么 Flawfinder 误报这么多？** 它只做词法匹配，不理解语法、宏和条件编译。看到危险函数名就报，分不清函数名和变量名，也不知道哪些代码在这次构建中根本没编译。
- **“有依据”是不是就等于漏洞？** 不是。它表示风险在源码层面成立；62 条里有一部分是可移植性或代码质量问题（比如负数右移依赖编译器实现），不一定能被利用。
- **为什么 clangsa 准确率反而比 Cppcheck 低？** clangsa 的告警集中在空指针等路径问题上，而像案例二那样“出错就退出”的约定写在文档里，它看不到，于是产生了较多误报。
- **复现环境耗时不一样吗？** 复现机器比原实验慢，耗时是原来的 1.3 到 4.7 倍，但三款工具的快慢顺序没有变化。
- **结论是谁判定的？** 725 条初步判定由 AI 对照源码给出，人工复核的抽样方案已经设计好，但复核尚未完成。
